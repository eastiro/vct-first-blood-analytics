# 站点审计 · 2026-10-25

对象：`site/index.html`（45 KB，单文件）+ `site/data/site_v3.json`（646 KB，15,715 回合）
方式：Playwright 实跑（1600 / 1280 / 1024 / 430 四档视口）+ 原始数据回算

**结论先说：页面没坏，0 console error、0 失败请求、无横向溢出、点击响应 16–58 ms。
问题不在"跑不跑得起来"，而在"分析深度"和"读图效率"两块。**

---

## 一、白捡一个维度没接：经济局（最高价值）

`data/rounds_all.jsonl` 里每回合有 10 条 `loadouts`，每个带 `spent`（本回合花的钱）、
`left`、`weapon`、`armor`。但 `90_site_data_v3.py` 只抽了 14 个整数，**经济字段一个都没进
`site_v3.json`**，所以页面上完全看不到买枪局。

可用性：**12,683 / 15,715 回合（80.7%）** 有完整双方花费。唯一缺的是中国 S2
（和坐标同一个原因，vlr.gg 没给该赛区回放）。

### 回算结果：经济差比补枪更基础

按"首杀方花费 − 对手花费"分三档：

| 首杀方经济 | n | 首杀→回合胜 |
|---|---|---|
| 优势（高 8,000+） | 3,250 | **78.7%** |
| 接近（±8,000 内） | 7,022 | 70.3% |
| 劣势（低 8,000+） | 2,332 | **63.1%** |

跨度 15.6 个百分点。极端格更狠：

| 首杀方 | 对手 | n | 首杀→胜 |
|---|---|---|---|
| 半买 | eco | 779 | **89.2%** |
| 全买 | eco | 1,038 | 85.2% |
| eco | 全买 | 601 | 57.4% |
| eco | 半买 | 410 | **47.6%** |
| 全买 | 全买 | 2,440 | 68.4% |

**拿首杀但经济输一档，胜率不到抛硬币。** 这句话现在的页面上说不出来。

### 而且补枪效应没有被经济混杂 —— 现有结论站得住

按同经济层内重算「被补 vs 没被补」：

| 首杀方买枪 | 被补→胜 | 没被补→胜 | 差 |
|---|---|---|---|
| eco | 51.7% (n=615) | 67.2% (n=1,648) | +15.5 pp |
| 半买 | 59.5% (n=1,002) | 77.5% (n=3,338) | +18.0 pp |
| 全买 | 59.2% (n=1,437) | 76.8% (n=4,564) | +17.6 pp |

全样本 18.7 pp，分层后 15.5–18.0 pp。**补枪是真效应，不是经济差的替身。**
（这一条本身值得写进 `RESULTS.md`，目前没有。）

**建议**：`site_v3.json` 每行加 2 个字段 `spentA / spentB`（或预先分好档位 0/1/2），
前端加一个"经济差"筛选行 + 一张 3×3 矩阵表。成本很低，收益最大。

## 二、热力图看不出热点（视觉最高优先级）

现状是"散点图 + 一层几乎看不见的模糊"：

1. **模糊层 `alpha .16` 在 1809 个点下等于没有**，实际渲染出来就是一堆红点。
2. **红点把底图盖住了**。VLR 小地图本身是暗灰调，密集红点叠上去只剩噪点。
3. **攻防区分失效**：热力层一律红色，只有 1.6–2.8 px 的圆/方去区分进攻/防守。
   1500 点以上根本分不清（见 `figures/_audit/01_default.png`）。
4. **"全部地图"模式是一团红斑**：12,677 个点叠在同一张 1024 空白画布上
   （`figures/_audit/07_allmaps.png`）。设计上是刻意的（躲开"10 张图共用一个网格"的问题），
   但结果没有信息量，不如不画。

**建议**（按性价比）：
- 换成 **hexbin** 或 **KDE 等值线**，攻防双色（红 `#ff4655` / 青 `#22d3ee`）分两层画；
- 或干脆做 **3×3 区域统计表**（A 点 / 中路 / B 点 / 各通道），表格比糊图更能回答
  "这队爱在哪打首杀"；
- "全部地图"模式换成 **per-map 小倍数图**（10 张缩略图）或 **地图×密度排行**，
  替换现在那团红斑。

## 三、无法回答"谁更强"：不能排序、不能比样本量

队伍表是站点最该被反复读的地方，但现在：

1. **固定按回合数排**，无排序。想按「首杀→胜」或「Meta Fit」排一下做不到。
2. **`slice(0, 40)` 硬截断**，62 支队里有 22 支永远看不到。
3. **8 列挤在一行**，队名一长，数字互相顶（`LOUD` / `Trace Esports` 那几行尤其挤）。
4. **没有样本量警示**：20 回合的队（±10 pp 噪声）和 300 回合的队并排列着，
   都显示一位小数，读者无法判断可信度。`RESULTS.md` 里算了 95% CI，页面上没有。
5. **没有全局基准对照**：`71.1%` 只出现在左侧卡片，表里没有 delta 列，
   所以"这队 75.9% 算好吗"要靠读者自己回忆。

**建议**：表头点击排序 + 去掉硬截断（改分页/虚拟滚动）+ `n` 列加 CI 或
小样本降透明度 + 加 `Δ vs 全局` 列。

## 四、状态不可分享

- **没有 URL 参数**。刷新即丢全部筛选，也没法把"霓虹 + 微风岛屿"这个视图发给别人。
- 没有导出（CSV / PNG）。
- 没有"重置筛选"。

对一个分析站点，这三条决定了它是"自己看的图"还是"能给别人看的东西"。

## 七、验证过、**不是** bug 的三条（避免白改）

1. **补枪 18.7 pp 不是经济混杂** —— 分层后仍 15.5–18.0 pp（见第一节）。
2. **LOUD 的「100% 阵容一致性 / Meta Fit」是真实的** —— 它在日落之城 225 回合
   只用一套 `chamber/neon/omen/sage/sova`。不是聚合 bug。
3. **6.5% 的回合是镜像阵容**（1023 / 15,715），真实存在
   （例：PRX vs LEVIATÁN on Lotus，双方都是 `jett/omen/raze/skye/vyse`）。

## 八、性能：不是问题，但会变成问题

- 首屏 JSON 646 KB，本地 `networkidle` 96 ms；点击筛选 16–58 ms。**现在没问题。**
- 但每次 `rebuild()` 会全表扫 **4–5 遍**：
  `busiestMapInScope` → `buildTeamSelect` → `agentsInScope` → `recompute`，
  外加 `renderAgents` 在选中英雄时再扫一遍。
  15,715 行无所谓；数据量翻 10 倍、或者开始按赛事累加多赛季，就该预建
  `byEvent / byMap / byTeam` 索引了。
- `agg()` 每行 `new Set([atkT, defT])`，15,715 次分配/刷新，可换成两次比较。
